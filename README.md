# STLC Agents PoC

PoC for STLC agents using Foundry and Microsoft Agent Framework.

This project demonstrates using Microsoft Foundry along with Microsoft Agent Framework to develop custom hosted agents that work for specific use-cases.

## Approach

These agents are designed to work in orchestration with other agents. The orchestration, in this usecase, will be handled by Copilot Studio. While requirement-analyzer and test-case-generator are also defined in Copilot Studio, a version of these are included here as well for reference.

### Test Executor

The test executor is a special agent which needs to do a lot more than the other agents. It needs to:

- Read the test scenarios generated by the test-case-generator and convert that into actual code.
- Save and commit the generated test files to a repository in a new branch.
- Trigger a pipeline to actually run the code it generated previously.

The test executor's only job is to write the tests and execute them. It does not wait for the tests to be completed. Instead, we will be triggering the bug logger agent directly, once the ADO pipeline completes.

### Flow

::: mermaid
sequenceDiagram
    Orchestrator ->> Test Executor: Generated test cases in an appropriate format.
    Test Executor ->> git_commit_push (tool): Generated code
    git_commit_push (tool) -->> Azure DevOps: Commit the generated test file and push it as a new commit.
    git_commit_push (tool) ->> Test Executor: Branch name where the code is pushed.
    Test Executor -->> Azure DevOps: (via MCP Server) Trigger pipeline with specified file name and branch name.
    Azure DevOps -->> Orchestrator: (or directly to Bug Logger) result of the test run.
:::

## Environment Setup

### Automatic setup

If running on a linux shell, simply run the `devsetup.sh` script using `./devsetup.sh` to install all dependencies.

### Manual setup

After [installing `uv`](https://docs.astral.sh/uv/getting-started/installation/), simply run `uv sync --dev` to install all dependencies.

Install prek pre-commit hooks using `uv run prek install`.

Add the foundry project endpoint and a deployed model name in `.env`. (Check out `.env.template` for reference.)

### Environment Variables

You need to use azure developer CLI to set the following environment variables:

- FOUNDRY_PROJECT_ENDPOINT
- AZURE_AI_MODEL_DEPLOYMENT_NAME
- AZURE_DEVOPS_PAT

To set them, run `azd env set <key> <value>`

### Foundry Toolboxes

Make sure your foundry project has the following toolboxes defined (preferably, with an ADO MCP server):

- test-executor-tools (required)
- requirement-analyzer-tools (optional, required if using requirement-analyzer)
- test-generator-tools (optional, required if using test-generator)

If you are only using the `test-executor` agent, you can skip creating the first two toolboxes.

Make sure all tools work with the project identity or some external key. Authentication via User OAuth might not work due to the agent not being standalone.

## Usage

To run the code locally, use `azd ai agent run`.

In another terminal, run `azd ai agent invoke --local` to invoke the running agent.

To deploy, use `azd deploy ...`.
You can specify which agent you wish to deploy, for eg. `azd deploy test-executor`.

Make sure all environment variables are correctly set before the deployment.

## Code

The codebase is intentionally kept simple. There are 2 main files we need to look at:

- `src/test_executor.py`
- `src/tools.py`

You can also find basic examples of other agents like `src/test_generator.py` and `src/requirement_analyzer.py`. However, for our PoC, they have been implemented in Copilot instead.

### Test Executor

Here, the code simply consists of a `PROMPT` definition and a `main` function. In our main function, we simply initialize a Foundry client, get the relevant tools, and then create the test-executor agent. The code then hosts the agent using a `ResponsesHostServer` which allows it to be hosted on Foundry.

### Tools

There are 3 tools that we have defnied in this project.

1. Foundry toolbox (`get_toolbox`) - as it is mentioned above, you need to create a foundry toolbox with the relevant tools your agent needs beforehand. The code then fetches that toolbox and makes it available to the agent. This allows us to keep the relevant tool definitions separate from the code. In our PoC, we only need the Azure DevOps MCP server in the toolbox.
2. `git_commit_push` - this tool allows the test-executor to commit and push a file to the repo. It uses the PAT token defined in the environment variable to access the git repository. The reason to keep this separate was that the current ADO MCP server doesn't allow us to make code changes. We instead rely on the DevOps Python SDK (which is just a wrapper around the ADO REST API).
3. `get_web_content` - this is a simple tool that essentially fetches a web URL and provides the contents to the agent. This allows the agent to check the page content before writing tests for the web page. This can later be extended to support more complex use-cases where we need to get the page DOM instead. For our usecase, a simple HTTP GET request seems to suffice.
