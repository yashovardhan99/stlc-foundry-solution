# STLC Agents PoC

PoC for STLC agents using Foundry and Microsoft Agent Framework.

This project demonstrates using Microsoft Foundry along with Microsoft Agent Framework to develop custom hosted agents that work for specific use-cases.

## Approach

These agents are designed to work in orchestration with other agents. The orchestration, in this usecase, will be handled by Copilot Studio. The requirement-analyzer, test-case-generator, and bug-logger agents are defined in Copilot Studio; this repository contains only the `test-executor` hosted agent.

### Test Executor

The test executor is a special agent which needs to do a lot more than the other agents. It needs to:

- Read the test scenarios generated by the test-case-generator and convert that into actual code.
- Optionally read the target repository and referenced GitHub issues for extra context.
- Save and commit the generated test files to a GitHub repository in a new branch, then open a pull request.
- Rely on the pull request to automatically trigger a GitHub Actions workflow that runs the generated code.

The test executor's only job is to write the tests and execute them. It does not wait for the tests to be completed, and it never merges the pull request. The bug logger agent is triggered automatically once the GitHub Actions workflow completes.

### Flow

``` mermaid
sequenceDiagram
    Orchestrator ->> Test Executor: Generated test cases in an appropriate format.
    Test Executor ->> GitHub (MCP server): (optional) read repo code / issues for context
    Test Executor ->> get_web_content (tool): Webpage URL
    get_web_content (tool) ->> Test Executor: Webpage contents (basic HTTP GET)
    Test Executor ->> GitHub (MCP server): create_branch + create_or_update_file + create_pull_request
    GitHub (MCP server) -->> GitHub: Commit the test file to a new branch and open a PR into main.
    GitHub (MCP server) ->> Test Executor: Branch name and pull request number/URL.
    GitHub -->> GitHub Actions: Opening the PR automatically triggers the test workflow.
    GitHub Actions -->> Bug Logger: On completion, the run result auto-triggers the bug logger.
```

After [installing `uv`](https://docs.astral.sh/uv/getting-started/installation/), simply run `uv sync --dev` to install all dependencies.

Install prek pre-commit hooks using `uv run prek install`.

Add the foundry project endpoint and a deployed model name in `.env`. (Check out `.env.template` for reference.)

To set them, run `azd env set <key> <value>`

### GitHub access

The test-executor connects directly to the remote GitHub MCP server (`https://api.githubcopilot.com/mcp/`, overridable via `GITHUB_MCP_URL`) from code, so no Foundry toolbox needs to be provisioned. It authenticates with a fine-grained GitHub PAT stored as an Azure Key Vault secret; the hosted agent identity reads it at runtime via the `Key Vault Secrets User` role.

The fine-grained PAT must grant, on the target repository:

- Contents: Read and write
- Issues: Read and write
- Pull requests: Read and write
- Actions: Read
- Discussions: Read
- Metadata: Read

The agent is restricted to a small client-side allow-list of GitHub MCP tools via `GITHUB_MCP_ALLOWED_TOOLS`; the default is `create_branch,create_or_update_file,create_pull_request,get_file_contents,search_code,issue_read,search_issues`. These tools are all provided by the GitHub MCP server's default toolsets, and the PAT permissions above govern what they can actually do.

- `AZURE_KEY_VAULT_URL` - the vault holding the PAT secret.
- `GITHUB_PAT_SECRET_NAME` - the secret name (defaults to `github-test-executor-pat`).
- `GITHUB_OWNER` / `GITHUB_REPO` - the target repository the agent commits to.
- `GITHUB_MCP_ALLOWED_TOOLS` - comma-separated allow-list of GitHub MCP tool names the agent may call.

The target repository must be initialized with a `main` branch and a GitHub Actions workflow that runs the committed tests on `pull_request` into `main` (the agent opens a PR from each `test-executor-**` branch).

## Usage

To run the code locally, use `azd ai agent run`.

In another terminal, run `azd ai agent invoke --local` to invoke the running agent.

To deploy, use `azd deploy ...`.
You can specify which agent you wish to deploy, for eg. `azd deploy test-executor`.

Make sure all environment variables are correctly set before the deployment.

## Copilot Studio integration

The orchestration and the other agents (requirement-analyzer, test-case-generator, bug-logger) live in Copilot Studio. The deployed `test-executor` is connected to that orchestrator as an external Microsoft Foundry agent.

To bind it:

1. Deploy the agent (`azd deploy test-executor`) and note its **Agent Id** and the **Foundry project endpoint** (`FOUNDRY_PROJECT_ENDPOINT`).
2. In Copilot Studio, open your orchestrator agent and go to **Agents** → **Add an agent** → **Connect to an external agent**.
3. Choose **Microsoft Foundry**, then supply the project endpoint and select the `test-executor` Agent Id.
4. Have the orchestrator route the generated BDD `.feature` content to this agent as the input message.

The agent's response reports the branch it created, the pull request it opened, and confirms that opening the PR triggered the GitHub Actions run. It does not wait for the run to finish and never merges the PR; the bug-logger agent is triggered automatically once the workflow completes.

## Code

The codebase is intentionally kept simple. There are 2 main files we need to look at:

- `src/test_executor.py`
- `src/tools.py`

### Test Executor

Here, the code simply consists of a `PROMPT` definition and a `main` function. In our main function, we simply initialize a Foundry client, get the relevant tools, and then create the test-executor agent. The code then hosts the agent using a `ResponsesHostServer` which allows it to be hosted on Foundry.

### Tools

There are 3 tools that we have defnied in this project.

1. GitHub MCP server (`get_github_mcp`) - connects the agent to the remote GitHub MCP server, which exposes the repository tools (`create_branch`, `create_or_update_file`, `push_files`, and more) the agent uses to commit generated tests. Authentication uses a fine-grained GitHub PAT read from Azure Key Vault, so no Foundry toolbox needs to be provisioned and a single credential covers all GitHub operations.
2. `get_web_content` - this is a simple tool that essentially fetches a web URL and provides the contents to the agent. This allows the agent to check the page content before writing tests for the web page. This can later be extended to support more complex use-cases where we need to get the page DOM instead. For our usecase, a simple HTTP GET request seems to suffice.
3. `validate_pytest_script` - A small static checker which can help the agent validate code syntax and basic correctness. It checks for Python parse errors, missing `test_` functions, common typos, and a few known bad patterns (such as lambda passed to `to_have_url`). This validation does not check full Playwright runtime/API correctness, but only for some narrow scenarios.
